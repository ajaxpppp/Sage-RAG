# Ragent 面试项目介绍策略与话术指南

## 一、核心原则：怎么让面试官对你的项目感兴趣

### 1.1 面试官在想什么

面试官听你介绍项目时，脑子里在评估三件事：
1. 这个项目有没有技术深度（不是 CRUD 套壳）
2. 你在里面做了什么（不是背别人的代码）
3. 你能不能讲清楚为什么这么做（不是只会 what，还要会 why）

### 1.2 三个吸引面试官的关键策略

**策略一：开场制造差异化**

不要说"我做了一个问答系统"，要说"我做了一个企业级 RAG 智能体平台"。RAG、Agent、MCP 这些词本身就是面试官的兴趣触发器。2025 年几乎所有技术团队都在往 AI 方向靠，你一开口就聊 RAG，面试官的注意力立刻就来了。

**策略二：用问题驱动而不是功能罗列**

不要说"我做了检索、做了对话、做了管理后台"。要说"企业知识库问答有三个核心难题：检索不准、模型不稳、成本不可控，我分别用多通道检索+Rerank、三态熔断器+模型路由、分布式队列限流来解决"。

面试官听到的是：你理解问题 -> 你设计了方案 -> 你落地了实现。这比罗列功能有说服力得多。

**策略三：主动埋钩子，引导面试官追问你擅长的方向**

介绍时故意留一些"半句话"，让面试官忍不住追问。比如：
- "检索引擎用了多通道并行架构，**其中有一个动态触发机制比较有意思**" -> 面试官大概率会问"什么动态触发机制"
- "模型路由里有一个**首包探测**的设计" -> 面试官会问"首包探测是什么"
- "限流方案不是简单的令牌桶，是**基于 Redis ZSET 的队列式限流**" -> 面试官会问"为什么不用令牌桶"

## 二、30 秒版本（电梯演讲）

适用场景：面试官说"简单介绍一下你的项目"

> "我做的是一个企业级 RAG 智能体平台，叫 Ragent。核心是把企业私有知识库和大模型结合起来，做精准的智能问答。
>
> 技术栈是 Spring Boot 3 + React 18 + Milvus 向量数据库。我主要负责了四个核心模块：多通道并行检索引擎、模型路由与三态熔断器、基于 Redis 的分布式队列限流、以及会话记忆的滑动窗口压缩。
>
> 整个 RAG 链路从查询改写、意图识别、多路检索、Rerank 精排到流式生成，都是我参与设计和实现的。"

要点：
- 30 秒内说完
- 包含项目名称、定位、技术栈、你的 4 个核心职责
- 每个职责都用了技术关键词，给面试官留追问空间

## 三、2 分钟版本（详细介绍）

适用场景：面试官说"详细介绍一下"

> "Ragent 是一个企业级 RAG 智能体平台，解决的核心问题是：企业内部知识库问答场景中，传统关键词搜索理解不了用户意图，直接用大模型又有幻觉问题。我们通过 RAG 架构把私有知识和大模型能力结合起来。
>
> 技术栈方面，后端是 Java 17 + Spring Boot 3，前端 React 18 + TypeScript，向量数据库用的 Milvus 2.6，还有 MySQL、Redis 做业务存储和缓存限流。
>
> 整个系统的核心链路是这样的：用户提问后，先加载会话记忆做上下文补全，然后查询改写和拆分解决指代消解问题，接着通过三级意图树做意图识别。识别完之后走多通道并行检索——一个通道基于意图定向检索，另一个通道做全局向量兜底，两个通道并行执行，结果经过去重和 Rerank 精排。最后组装 Prompt 发给大模型，通过 SSE 流式返回。
>
> 我重点负责了四个模块：
>
> 第一个是多通道检索引擎。核心设计是把检索策略抽象成 SearchChannel 接口，通过 CompletableFuture 并行执行，后面接去重和 Rerank 的后处理链。当意图置信度低于 0.6 时会自动触发全局向量检索兜底。
>
> 第二个是模型路由和熔断。因为生产环境不能只依赖一个模型厂商，我设计了 ModelRoutingExecutor 按优先级路由多个模型，配合三态熔断器做故障隔离。还有一个首包探测机制，切换模型时先缓冲第一个响应包，确认正常后再输出，用户完全无感知。
>
> 第三个是分布式队列限流。大模型调用成本高，需要控制并发。我用 Redis ZSET 做分布式等待队列，Lua 脚本保证原子性，Pub/Sub 做跨节点通知，本地 Semaphore 控制单机并发。用户排队时通过 SSE 实时推送位置。
>
> 第四个是会话记忆管理。用滑动窗口保留最近 10 轮对话，超出的部分自动调 LLM 生成摘要，摘要缓存到数据库。这样既控制了 Token 成本，又不丢关键上下文。"

## 四、面试官追问应对策略（15 个高频问题）

### 4.1 项目整体类

**Q: 为什么选择自己实现 RAG 而不是用 LangChain4j？**

> "LangChain4j 更适合快速原型，但企业场景需要更细粒度的控制。比如我们的多通道检索需要根据意图置信度动态决定走哪些通道，后处理链需要自定义去重和 Rerank 逻辑，这些用 LangChain4j 的抽象反而会受限。而且 LangChain4j 版本迭代很快，低版本功能缺失，高版本升级约等于重写，自己实现核心链路可控性更强。"

**Q: 项目的并发量大概是多少？怎么做的压测？**

> "这是一个面向企业内部的知识库问答系统，并发量不会特别大，但大模型调用本身响应慢、成本高，所以瓶颈不在 QPS 而在并发控制。我们通过分布式队列限流控制同时调用大模型的请求数，默认配置是单节点最大 10 个并发。压测方面主要关注的是检索延迟和端到端响应时间，多通道并行检索的 P99 延迟控制在 500ms 以内。"

**Q: 你们团队几个人？你负责哪些部分？**

> "核心开发 3 个人，我主要负责后端的 RAG 核心链路，包括检索引擎、模型路由熔断、限流和记忆管理。前端是另一个同学负责的，我会看前端代码但不是主要开发者。文档摄取流水线是一起设计的，我负责了其中的分块策略和向量化部分。"

### 4.2 检索相关

**Q: 为什么不用 Elasticsearch 做混合检索？**

> "我们评估过 ES 的 dense_vector 字段，但 Milvus 在纯向量检索场景下性能更好，支持 HNSW、IVF_FLAT 等多种索引类型，而且 Milvus 2.6 原生支持标量过滤+向量检索的混合查询。ES 的优势在全文检索和 BM25，如果后续要加关键词检索通道，可以把 ES 作为一个新的 SearchChannel 接入，架构上是完全支持的。"

**Q: Rerank 的原理是什么？为什么需要 Rerank？**

> "向量检索是基于 Embedding 的近似最近邻搜索，召回的是语义相似的文档，但相似不等于相关。Rerank 模型（我们用的 BGE-Reranker-v2-m3）是一个交叉编码器，它把 query 和每个候选文档拼接在一起做精细的相关性打分，比双塔模型的 Embedding 相似度更准确。代价是 Rerank 比较慢，所以我们先用向量检索召回 top-20，再用 Rerank 精排取 top-5。"

**Q: 意图识别置信度低于 0.6 时触发全局检索，这个 0.6 怎么定的？**

> "这个阈值是通过实验调出来的。我们用了一批标注好的测试问题，分别测试不同阈值下的检索准确率和召回率。0.6 是一个平衡点——太高会导致大量请求走全局检索，增加延迟和成本；太低会导致意图识别错误时没有兜底。这个值在配置文件里可以动态调整。"

### 4.3 模型路由与熔断

**Q: 熔断器为什么不用 Resilience4j 或 Sentinel？**

> "Resilience4j 和 Sentinel 是通用的熔断限流框架，但我们的场景有特殊需求：模型调用是流式的，需要首包探测机制——切换到新模型时要先缓冲第一个响应包确认正常，再开始输出。这个逻辑和通用熔断器的 fallback 机制不太一样，自己实现更灵活。而且我们的熔断粒度是模型级别的，每个模型独立维护状态，实现起来也不复杂，核心就是一个 ConcurrentHashMap + AtomicInteger。"

**Q: 首包探测具体怎么实现的？**

> "ProbeBufferingCallback 是一个装饰器，包装了原始的 StreamCallback。当模型路由切换到一个新模型时，ProbeBufferingCallback 会拦截第一个 onToken 事件，先缓冲起来不发给用户。如果后续正常收到更多 token，说明模型可用，就把缓冲的内容一起发出去。如果第一个包就超时或报错，就标记这个模型不可用，切换到下一个候选，用户端完全无感知。"

### 4.4 限流相关

**Q: 为什么不用令牌桶或滑动窗口限流？**

> "令牌桶和滑动窗口适合控制 QPS，但我们的场景不是控制每秒请求数，而是控制同时在处理的请求数。大模型调用一次可能要 10-30 秒，用令牌桶的话令牌很快就发完了，后面的请求直接被拒绝。我们需要的是排队机制——请求进来排队等待，前面的请求处理完了后面的自动顶上，同时还要告诉用户你排在第几位。ZSET 的有序特性天然适合这个场景。"

**Q: Pub/Sub 通知会不会有惊群效应？**

> "会有，所以我们做了本地合并通知。收到 Pub/Sub 消息后不是每个等待线程都去抢，而是由一个本地的通知线程统一处理，检查 ZSET 队首是否是自己，是的话才唤醒对应的等待线程。这样避免了所有节点的所有等待线程同时去 Redis 查询。"

### 4.5 记忆管理

**Q: 摘要压缩会不会丢失关键信息？**

> "会有信息损失，这是 trade-off。我们的策略是：摘要 Prompt 会明确要求保留关键实体、数字、结论等信息，尽量只压缩冗余的对话过程。而且最近 10 轮对话是完整保留的，摘要只针对更早的历史。实际测试下来，对于大多数多轮对话场景，用户关注的信息通常在最近几轮里，摘要丢失的信息对回答质量影响不大。"

**Q: 如果用户问的是很早之前聊过的内容怎么办？**

> "这确实是一个边界场景。目前的方案是摘要里会保留关键信息，大部分情况能覆盖。如果要做得更好，可以考虑对历史消息也做向量化，用户提问时不仅检索知识库，也检索历史对话。这个作为后续优化方向已经在规划中了。"

### 4.6 工程能力类

**Q: 8 个线程池为什么不用一个统一的线程池？**

> "不同任务的特性差异很大。比如模型调用是 IO 密集型，等待时间长，需要较多线程；意图识别是 CPU 密集型，线程数不宜过多。如果共用一个线程池，模型调用的长时间占用会饿死其他短任务。独立线程池可以针对每种任务的特性单独调优，互不影响。而且出问题时也容易定位——看哪个池的队列满了就知道瓶颈在哪。"

**Q: TTL 上下文传播是怎么做的？**

> "用的阿里开源的 TransmittableThreadLocal（TTL）。普通的 ThreadLocal 在线程池场景下会丢失，因为线程是复用的。TTL 通过包装线程池的 execute/submit 方法，在任务提交时捕获当前线程的 ThreadLocal 值，在任务执行时恢复。我们用 TtlExecutors.getTtlExecutorService() 包装所有线程池，确保用户上下文（userId、role）和链路追踪上下文（traceId）在异步线程中不丢失。"

## 五、面试节奏控制技巧

### 5.1 开场 30 秒定基调

前 30 秒决定面试官对你项目的第一印象。要做到：
- 说出项目名称和一句话定位
- 点出 2-3 个技术关键词（RAG、多通道检索、模型熔断）
- 明确你的 4 个核心职责

### 5.2 中间用"问题-方案"结构

每讲一个模块，先说遇到了什么问题，再说你的方案。这比直接说"我用了 XXX 技术"有说服力得多。

示例：
- 不好的："我用了 Redis ZSET 做限流"
- 好的："大模型调用成本高、响应慢，传统令牌桶控制的是 QPS 不适合这个场景，所以我设计了基于 Redis ZSET 的队列式限流，支持排队等待和实时位置推送"

### 5.3 主动引导追问方向

如果你对某个模块特别熟，就在介绍时多留一些"钩子"。比如：
- "这里有一个比较巧妙的设计是..."（然后不展开）
- "这个方案还解决了一个额外的问题..."（然后一笔带过）

面试官大概率会追问，而你已经准备好了答案。

### 5.4 不会的问题怎么办

如果被问到不熟悉的细节，诚实说"这部分我了解大致原理但没有深入实现"，然后把话题引到你熟悉的方向。比如：

> "Milvus 的 HNSW 索引的具体参数调优我没有深入研究，但在检索层面我更关注的是多通道的编排策略和后处理链的设计，这部分我可以详细聊聊。"

## 六、面试官可能的"陷阱"问题

### 6.1 "这个项目是你自己写的还是开源项目？"

> "这是基于一个开源项目的架构做的二次开发和深度定制。核心的 RAG 链路、检索引擎、模型路由熔断、限流方案都是我自己设计和实现的。我选择这个项目是因为它的架构设计合理，但很多核心模块需要根据实际业务场景做深度定制，这个过程让我对 RAG 系统有了很深的理解。"

### 6.2 "你说的这些设计模式是不是过度设计？"

> "每个设计模式都对应一个具体的扩展需求。比如 SearchChannel 接口不是为了用策略模式而用，是因为我们确实需要动态增减检索通道——后续要加 ES 关键词检索通道时，只需要实现接口注册为 Bean 就行，不用改任何已有代码。如果只有一个检索方式，我不会抽象接口。"

### 6.3 "向量数据库挂了怎么办？"

> "Milvus 本身支持集群部署和副本机制，生产环境会配置多副本。如果 Milvus 完全不可用，检索引擎会捕获异常，返回空结果，大模型会基于自身知识回答并提示用户'当前知识库暂时不可用'。不会导致整个服务挂掉。"
